### 3-a 実測：M PLUS Rounded 1c と今の system rounded（同じ pt）

## §2 3案から「採るべき所」（実装リスクの面から）

**B1 サクセス路線**
- **波0（壊れて見える所を先に小コミットで消す）と、`FlipCard` を捨てずに作り直しへ持ち越す設計**（§3 順2）。不具合修正がそのまま新部品の第一歩になり、二度手間が無い。
- **「`.compact` は現行 adviceBox と1pt違わず同じ」「`StageScene(.keiko)` は差分ゼロ」**（C08・C12）＝部品の切り出しはスクショ差分ゼロで確かめる、という回帰の作法。3案共通の規則にする。
- `PressableStyle(silent: true)` で押下音の二重鳴りを避ける（C09）／**最下帯の高さを定数化してトーストの位置を守る**（C11）＝衝突を自分で拾えている。
- 「先に beat を enum にする」（C24）＝方向は正しい（コミットを分ければよい・X4-15）。
- 判の共有部品化を「大会結果（C22）の後に年末（C26）」の順に置く依存の読み。
- デバッグ導線（`MZ_UI`／`MZ_SMOKE`／`MZ_FIN`）を全画面で保つ約束（§4-3）。

**B2 舞台演出路線**
- **§4-3「X4 への先回り」**：`burstHold`・`pulledID`・`.task(id: session.week)` の3本・トーストの位置を不変と明言し、**W1〜W5 の実プレイ録画で Beat2 の秒数が同じことを確かめる**＝週メインを守る検証の型として3案共通にする。
- **B-02（イベントが獲得の一拍に被る）は原因の実機ログが先**として待ち時間に触らない判断（§3 末尾・§5-16）、`fullScreenCover` のせり上がりを日常の遷移として残す判断（§2-5）＝一番安全な線引き。
- **`FinalsData` の乱数の引き順を変えず、名前・年は引数で足す**（§2-8）＝表示の決定性（スクショ比較）を守る。
- 「常時動く `TimelineView` は1画面2本まで」という予算そのもの（守らせ方は X4-18）。儀式の2回目以降の短縮版（0.8秒）とタップで飛ばせる規定。
- 共用部品（回想⇄勇退・レーダー・波形）は両方の画面のスクショをコミットに付ける（§4-3-4）。
- フォント修正の直後に全画面を一巡して撮り、以後の before 基準にする（§4-3-5）。
- 最小到達版の切り方（§4-2）＝第1便の線を先に引いてある。

**B3 情報設計路線**
- **順番**：土台（見た目ほぼゼロ）→不具合→画面を頻度順。直列区間が3案で一番短く、worktree 並列の効きが一番大きい。
- **段トークンへの移行は画面ごとのコミットで**（§1-2 末尾）＝一括置換をしないので部分的に戻せる。旧 `Font.maru(_:weight:)` を残して移行する作法。
- フォント修正は `fixedSize` で固定→**Dynamic Type は最後**（C18）、かつ上限と `ViewThatFits`／`@ScaledMetric` を部品ごとに先に決めてある（§1-9-1）＝最後の一斉見直しが軽くなる。
- **Beat2 を触る前に B-02 の時刻ログ（C2）→「チップ最低0.6秒の後に全画面」の順序確認（C13）**＝状態機械の変更に検証の順番が付いている。
- **待ち時間の規格表（§1-9-7）**：場面ごとの「入力を止めてよい最大・畳めるか・解放の最小表示」。Beat2・大会結果・決勝の状態機械を作り直す時の受け入れ基準としてそのまま使える。
- Reduce Motion は `Juice.swift` の4部品の入口で判定（呼び出し側無改修）・**音と触覚は止めない**（3案とも入口判定は同じ＝ここは統合で揉めない）。
- 描画負荷が3案で一番軽い（常駐ループを増やさない）。


## §3 統合するならこう組む

見た目の路線（明るい舞台か、照明の緩急か）はリードとオーナーの判断に任せ、**実装の骨は「B3 の順番・B2 の守り方・B1 の差分ゼロの切り出し」で組む**。①まず骨組みの1コミット（使う新規ファイルを空の型で全部作って pbxproj を1回で確定・`WaveformView`／`RaysView`／`ConfettiView`／判の部品・背景1枚1ファイルを独立させる）と、フォント名の修正＋溢れ直し（1〜1.5日・§1-補3 の当たり表を潰し、402／375×812／375×667 の3機で before を撮る）を入れる。②次に**見た目ゼロの状態機械を3本**だけ先に作り直す：Beat2 を保持 Task へ（X4-04・W1〜W5 の録画で秒数一致）、大会結果の開示列を保持 Task＋スキップ可へ（X4-08）、決勝の beat を enum＋時間駆動の駆動役へ（今と同じタップ駆動のまま・X4-15/16）。同時に SoundManager に取り消し可能なフェードとダック倍率を入れる（X4-13）。ここまでがリードの直列（約5〜6日）。③B3 の Phase A（トークン・段・`.hardShadow`・`PressableStyle`・Reduce Motion の入口）と B1 流の部品切り出し（現行と差分ゼロをスクショで確認）を入れ、3案共通の不具合修正を1不具合1コミットで流す。④その後に §1-補2 のレーン（I・E・T・R・F・N・S）を2〜3本ずつ worktree に出し、目視はリードの simulator で直列に受ける。演出は B3 §1-9-7 の待ち時間の表を受け入れ基準にし、儀式・幕は RootView に重ねず「入口で再生し終えてから状態を進める」形（X4-11 ①）、`StageFrame` は動くものを1枚の Canvas・30fps に畳む（X4-18）。**やらないこと**：イベントの cover の作り直し（X4-07）、週メインの字の段の一括入れ替え（X4-29 は4分割で）、`.system`／明朝の一括置換コミット。この組み方で合計は約26〜30日【仮】（どの路線の見た目を載せるかで±5日）、最初の便（不具合＋イベント＋大会結果）は約9〜10日【仮】。
