# 紙講評「直近に出た文を避ける履歴」の効果の実測 v0

**材料・コード不変**（2026-10-25・懸念の台帳 L41 の対策案①の材料）。GameCore・アプリ・テストは変えていない。判断はオーナー。推奨は書かない。

## 要点3行
1. 基準（今のまま）の読み返し率は A 6.5%・B 9.4%・C 10.1%。**前回の実測（11.1/15.3/18.2%）より4〜8pt低く、±3ptに収まらなかった**（原因は材料の節）。案①の効き目は、この再実測の基準に対する差で読むこと。
2. 「直近N回を避ける」は **N=3〜10 では効きが小さい**（Cで 10.1→10.0→9.9→9.4%）。N=20 で7.5%、N=40 で3.0%、**無限（キャリア内で未出の文を優先）なら 0%・同じ文の最多は1回**。
3. 読み返しの大半は「10本以上前の文」との再会。しかも紙講評は**1つのプール（相性が高く通過）に約6割が集中**（24本・A型は8割超）なので、短い履歴では間に合わない。

## 材料
- 実測コード：`scratchpad/readback/`（Swift 実行パッケージ・GameCore にパス依存・コミットしない）。前回と同じ方法：`WeekRunner` を10年回し、`.weekDone` の `isStage` 結果（GP決勝は除く）ごとに `Scene.from(...)`・`salt = year*131 + week`。ボット・3型（A: 能力を各年頭に10へ抑える／B: 35を下限／C: 1〜3年目35・4年目から60下限）・20シード（1001〜1020）は前回の記述どおり。
- 紙講評の候補プールの取り出しは `JudgeTalk.paperReview`（GameCore/JudgeTalk.swift:467）の写し。JudgeTalk.swift を丸ごとコピーして内部の `Paper`・`mix`・`fill` を直接呼んだ。**基準の出力は本物の `paperReview` と 5918 件中 0 件の不一致**（検算済み）。
- 案①の写し：選ばれた候補の位置 `mix(salt,21) % プール数` から、**表示される完成文（{題}・差し込み口を埋めた後）が直近N回の表示に入っていれば、次の位置へずらす**（プール末尾から先頭へ回る・全部被れば元の文）。salt は変えない・乱数は消費しない。履歴の単位は完成文。N=無限は「そのキャリアで一度も出ていない文を優先」。
- 数字は20キャリアの合算の率、キャリア最大、同じ文の最多（全キャリアの最大／1キャリアの最多回数の平均）。避けても場面（Scene）の列は変わらない（乱数非依存）ので、同じ場面列に対して全方式を比べている。
- **基準が前回とずれた理由（確定ではない）**：総本数は合わせられた（A78.1／B110.9／C107.0＝前回77.7／109.8／105.1）。A型は夜逃げ・解散で10年未満に終わるため、年の終わりにフラグ（夜逃げ・解散）を戻して10年続けさせた。それでも率が低い。前回のボットのネタ選び・ネタ名の付き方・シードの違いが候補と思われるが、前回のコードが残っておらず突き合わせられなかった（ネタ枠を1〜4に変えても率はほぼ動かない＝ネタ名の影響ではない）。絶対値は目安、N 間の比較は同じ列での差なので有効。

## 読み方（判断はオーナー）
- 直近3〜10回を避ける素朴な案は、読み返しをほぼ減らさない（Cで 0.2〜0.7pt）。「同じ文を続けて見る」は元から起きにくく、反復は離れた回の再会が主だから。
- 効かせるには「そのキャリアで出た文」を広く覚える必要がある（20回で約2.6pt減、40回で約7pt減、無限で全消し）。無限でも履歴は文字列でなく**プール内の位置とsaltだけ**を持てば足りる（完成文は再計算できる）。
- 無限で全て避けられたのは、プールが最小でも5本（遠い敗退）あり、かつ差し込み口（入り・中・一言・締め）の組み合わせで完成文の種類が多いため。**プールの文の種類（テンプレート）で見ると**、「相性高く通過」24本が約6割を担うので、同じ“型の文”はもっと頻繁に再会する（テンプレート単位の再会率は A39%・B51%・C55%。差し込み口の語が変わるため完成文では被らない）。完成文が違っても「同じ文型」と読まれるかは目視の判断（今回の実測の外）。
- 避けるとプール内で別の文に回るので、「その場面に一番合う文」からずれる度合いが増える（プールは場面ごとに既に選別されているので、同プール内のずれのみ）。

## 実装する場合の場所の見当（本書では変更しない）
- 窓口は `ManzaiGame/Sources/JudgeData.swift` の `review(...)`（`JudgeTalk.paperReview` を呼ぶだけ）。避ける処理は GameCore の `paperReview` に「除外集合（完成文または位置の履歴）」の引数を足す形が自然（乱数非消費・既定は空＝golden・既存テスト不変）。
- **履歴を持つ場所**：`TournamentResultView.body`（TournamentResultView.swift:95）は描画のたびに `review` を呼ぶので、ここで履歴を更新してはいけない（再描画で履歴が進み文が変わる）。結果が確定する時点（`GameSession` が StageResult を受けて結果画面へ渡す所）で1回だけ「表示した文」を履歴に追記し、`body` はその時点の履歴スナップショットから決定的に引く形にする必要がある。
- **セーブに入れるか**（論点）：入れる→再起動・中断復帰で文が同じ・履歴が続く（`SaveData` に Optional な配列を足す・旧セーブは空で復号＝既存の流儀）。入れない→再起動で履歴が消え、結果画面を開き直すと別の文になりうる／履歴が短くなる。無限案は履歴が最大約110件（文字列なら数KB・位置なら数百バイト）。
- 乱数非消費・golden 不変・UI層のみで足りるかは、`paperReview` を GameCore 側に残す限り GameCore の公開関数のシグネチャ変更（既定値つき）が要る点だけ注意。
