## 1. 論点A — 会話を全廃して無会話シミュレーションにするか

### 1-1. ブルーチーム最終弁論（会話を残す）

1. **会話はもう「在庫」ではなく「配線済みの実装」**（§0-1）。`DialogueData.innerVoice` は週頭に状態駆動で呼ばれ、`ChoiceEventOverlay` は確定発火6本＋週次抽選を回している。全廃は削除作業＝**新規コストの発生**であって節約ではない。
2. **既に「間引き案」が実装済み**。`DialogueData.swift` 冒頭のコメントが明示する: 「常時出るのは俺の独白（助言・嘆き・人間味）。**ボケない**。谷口/先輩の会話は将来レアイベントで（毎週は出さない）」。依頼文の選択肢②「要所に絞る」は**既に採用され動いている状態**であり、今から決める話ではない。
3. **オーナーの不満「Claudeが考える会話は面白くない」は、現行の常時テキストには当たっていない可能性が高い**。常時出ているのは「会話」ではなく**一人称の心の声**で、`manzai-drama-voice` SKILL は「**ボケ/オチ/パンチラインを一文字も書かない**」を憲法にしている＝Claudeが最も弱い「面白いボケを書く」を構造的に回避する設計になっている。不満の対象がどのスロットの何行目なのか、**1件も特定されていない**（SIMULATOR_FEEDBACK 0件）。
4. **Skillは「未活用」ではない**。`neta_system_redesign_v2`（ネタおろし一言）・`exp_earning_loop_ux_reply_v0`（新規文言5つ）はいずれも drama-voice 採点済と記録されている。
5. 全廃すると `ChoiceEvent` 機構（252行＋474行）が**テキストのない選択肢**になり、機構ごと死ぬ。イベント＝週次の起伏の唯一の供給源。

**都合の悪い事実**: それでも「面白いかどうか」は一度も第三者に測られていない。ブルーの主張は「壊すな」であって「面白い」の証明ではない。

### 1-2. レッドチーム最終弁論（会話を切る）

1. **オーナーが自分の作品のテキストを面白いと思っていない。** これは測定値より重い。作者が読み返したくないテキストを増やす運用は、個人開発では必ず止まる（実際7週間止まっている）。
2. **執筆・レビュー・配線は依然として最大のドレイン**（`game_reality_check_v0` §4）。7月の高密度コミットの相当部分が会話・イベント・講評の配線に消えている。
3. **会話は「面白い」に届かないと逆効果**。無会話の数値ループは「素っ気ない」で済むが、滑った会話は「寒い」になる。期待値がマイナスに振れうるのはテキストだけ。
4. 数値ループ主体の育成シムはジャンルとして成立する。会話は差別化の**必要条件ではない**。

**都合の悪い事実**: 全廃しても浮く工数は「これから書く分」だけで、**既に書かれた分は戻ってこない**。さらに削除＋回帰確認という新規コストが乗る。「時間がない」を理由に全廃するのは、時間の使い方として合理的でない。

### 1-3. 裁定 — **KEEP（ただし「凍結」＝今ある分で出す・1行も増やさない）**

| 対象 | 裁定 |
|---|---|
| 配線済みの会話・心の声・選択肢イベント（現状分） | **KEEP**（一切触らない） |
| 新規テキストの執筆・増産（batch2-4、未配線proposal 0002-0008 等） | **CUT**（リリース前はゼロ） |
| 決勝敗退の山場テキストの推敲（差し替えのみ・増量なし） | **DEFER**（§5の全項目が終わって時間が余ったら） |
| 会話の全廃 | **却下** |

**理由**: 三択（全廃／間引き／Skillで底上げ）はいずれも**追加作業を要求する**。追加作業ゼロで出荷に最も近いのは第四の選択肢「現状で凍結」。間引きは既に実装済み（§0-1）、Skill運用は増産を前提とし、全廃は削除コストがかかる。**リリースを早めるという単一目的の下では、会話に関して今やるべき作業は無い。**

**工数【仮】**: 凍結＝**0時間**／全廃＝8〜12時間（削除＋イベント機構の代替＋回帰目視）／Skill運用で底上げ＝1スロット30〜60分×数十スロット＝**20〜60時間**。
**リリース日への影響**: 凍結＝**変わらない**（＋増産計画を捨てることで20〜60時間を回収）。全廃＝**1〜2日遅れる**。底上げ＝**2〜4週間遅れる**。

**「面白くない」問題への処方（工数ほぼゼロ・リリース非ブロック）**:
リリース前にやるのは執筆でも全廃でもなく**特定**。`SIMULATOR_FEEDBACK.md` に用意済みの書式（スロット／本文／状況／感じたこと）で、**通しプレイ中に寒いと思った文だけを写す**。集まった件数で分岐する——
- 0〜2件 → 問題は会話ではない。凍結のまま出す。
- 3件以上 → **その特定されたスロットだけ** drama-voice で書き直す（1件30分【仮】）。全面底上げはしない。

### 1-4. 【設計上の懸念】

- **会話のCUTは後戻り困難。** `ChoiceEvent`（GameCore 252行）・`ChoiceEventOverlay`・`ChoiceEventData`・`DialogueData` は `GameSession`／`WeekMainView` に相互に食い込んでおり、テキストだけ抜く分離線が引けない。剥がした後で「やっぱり要る」となった場合の復旧コストは削除コストを大きく上回る。**この判断だけは "後で決める" を選べる余地がある側（＝残す側）に倒すべき。**
- `DialogueData` は `Codable`（中断セーブの復元対象）。除去はセーブ互換の破壊を伴う＝**リリース後に外すのは実質不可能**。

## 2. 論点B — UI/UXのどこまでをリリース前に直すか

### 2-1. ブルーチーム最終弁論（直してから出す）

1. **8件の指摘は1件も着手されていない**（§0-2）。「もう半分やってある」ではなく**丸ごと未処理**。
2. オーナー自身の一次所感が「**見たけど全くパワプロっぽくもないしゲームっぽくない**」。作者本人が起動して離脱している画面を初見の他人が10分触るのは無理がある。検証①以前の問題。
3. **凡例追加・ボタンの立体感・罫線は実装コストが低い割に効果が大きい**と `redteam_uiux_v0` §5 自身が明記。安いものまで見送るのは節約になっていない。
4. **表情差分のコスト前提が変わっている**。`docs/art_order_sheet_v0.md`（2026-08-02）が既に画像生成AI用のプロンプト集として完成しており、「イラスト外注」ではなく**オーナーがプロンプトを貼って3〜5回引き直す1〜2時間の作業**に落ちている。さらに `CharacterAvatars.swift`（146行）は手続き生成の顔グラが既に動いており、**眉と口の形を3種足すだけで表情差分は実装できる（イラスト不要）**。レッドの「ここが最も工数を圧迫する」という論拠は現物と合わない。

**都合の悪い事実**: それでも全件やれば数十時間。8件を「全部重要」と扱えば7週間の停止が8週間になるだけ。

### 2-2. レッドチーム最終弁論（ちゃちくても出す）

1. `game_reality_check_v0` の結論は「**本を読むな、実機で10分遊べ**」。UI磨きはその最新形の言い訳になりうる。**現に磨きの計画（レビューdoc）が出た瞬間に7週間止まった**——これは仮説ではなく観測された事実。
2. **「やる気（テンション）ゲージ」は機構ごと存在しない**（grep でヒット0。GameStateにあるのは stamina / mental / money / fame / compat）。これは表示の話ではなく**新機構の要求**＝リリース前に触れば確実に遅れる。指摘を額面通り全部受けると、こういう "実は新規開発" が紛れ込む。
3. 配色の全面刷新（クリーム系→原色＋黒縁）は `Theme.swift` 296行を全画面が参照している。ここを触ると**全画面の再目視**が必要（規律D-10）＝単体で1〜2週間級。
4. 最初のリリースは反応を買う行為であり、磨きは反応を見てからの方が総工数が少ない。

**都合の悪い事実**: 「ちゃちくても出す」が通るのは**動作が分かる**場合に限る。押せると分からないボタン・凡例のない暗号バッジは "ちゃちい" ではなく **"操作不能"** で、これは美観の問題ではない。

## 3. 論点C — 賞レース構造の理解不足という指摘への対応

### 3-1. ブルーチーム最終弁論（調査を深める）

1. 笑い・賞レースのクラフトは `game_reality_check_v0` §5 が**唯一「本を買う価値がある」と認めた領域**＝moat。他ジャンルの育成SLGと差別化できるのはここだけ。
2. 一次資料は安価（新書1冊）で、審査員講評・ネタ資産の説得力に直結する。
3. **構造理解と法務リスクは別レイヤー**。`legal_risk_v0` §4 の危険物は「氏名・似顔絵・賞レース名・番組名・経歴（＝同定要素）」であって、**尺・構成技法・採点作法・出順効果といった "構造" は §4-2 のどの行にも該当しない**（アイデアは商標・パブリシティ権の保護対象ではない）。構造を学ぶこと自体は法務的に無色。
4. 現状 `judge_preference_research_v0` §5 の相性表は**表示専用**で、「今年のパネルの配合を読んでネタ型を当てにいく」という読みのゲームは成立していない。

**都合の悪い事実**: 相性をスコアに乗せる（1-b）は**規律A発動＝golden全再測**。`exp_issuance_verification_v0` の到達率アンカー（やり込み45.0% / のんびり22.9% / バランス8.8%【仮】）が動き、sim較正5ゲートをやり直すことになる。

### 3-2. レッドチーム最終弁論（調査を切る）

1. **「甘さ」の正体は理解不足ではない。** 調査docは既に2本（`judge_preference_research_v0` 155行・`neta_system_redesign_v2` 363行）あり、翻案も終わり、**ネタは既に合否スコアに効いている**（Phase 1-a・`netaScoreBonus = polish×0.04 + buzz×0.02`・決勝2本制ペナルティ付き）。7審査員の固定嗜好も決勝の見せ札ラベルとして画面に出ている。**未配線なのは1-b（型×審査員相性のスコア化）1点だけ。**
2. その1-bは**オーナー自身が「試遊後に判断」で据置を確定済み**（`future_slot_impl_v0` 2026-07-20）。**既に決まっている判断を蒸し返している。**
3. 追加調査は必ず「寄せたくなる誘惑」を強める。`legal_risk_v0` §4-f は「**最も危険なのは本編より"実在に寄せるマーケティング"**」と名指しする。構造を深く知るほど、紹介文やストア説明で "あの空気" を出したくなる圧が上がる。
4. そして何より——**調査は7週間の停止を解かない**。読書もdoc執筆もコミットを1件も生まない。

**都合の悪い事実**: 相性が総合点一本に潰れたままだと、7審査員は「割れて見えるだけの飾り」に留まる。moatは表示層にしか無い。

### 3-3. 裁定 — **追加調査は CUT / 1-b（相性スコア化）は DEFER / 現状水準で十分**

| 対象 | 裁定 | 理由 |
|---|---|---|
| 一次資料の追加調査・架空翻案の続き | **CUT**（リリース前） | 調査2本＋Phase 1-a配線済＝moatは既に実装層に到達している。追加投入分の行き先が無い |

**「甘い」の切り分け結論**: 甘さの原因は**構造理解の不足ではなく、構造が総合点一本に潰れて画面から読めないこと**。そしてそれを解く鍵（1-b）は golden 全再測という最も高い代償を要求する。**つまり "甘さ" はリリース前に解けない種類の問題である。** ここを認めるのが最短ルート。

**工数【仮】**: 追加調査＝20〜40時間／1-b＝実装8〜12h＋golden再生成＋sim較正5ゲート＋優勝率再較正＝**16〜30時間＋バランス崩壊リスク**。
**リリース日への影響**: CUT/DEFERで**変わらない**。実行すれば**1〜3週間遅れる**（1-bは加えて既存バランス検証の信頼性を一時的に失う）。

### 3-4. 【設計上の懸念】

- **1-b は後戻り困難。** 1-a（`selectedNetaID` ゲートで golden 経路恒等0）と違い、1-b は **golden キャリアにも常時効く**（`future_slot_impl_v0` の記述通り）。入れた後に「やっぱり戻す」＝再びgolden全再測。**リリース前に触れてはいけない**ことを再確認する。
- **調査を深める行為自体に法務リスクの"間接的な"上昇がある。** `legal_risk_v0` §4-g の安全基準は「同定要素の総体を切り離す」。構造の理解が深まるほど、翻案の粒度が細かくなり「特定できる経歴・エピソード」(§4-g-d) の混入確率が上がる。追加調査を再開する場合は、**§4-g の6項目チェックを執筆の門に置く**ことを条件にする。
