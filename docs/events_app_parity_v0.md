# 実測のイベント抽選をアプリに合わせる（EVENTS_APP） v0

要点
- `tools/sim_career.py` に `EVENTS_APP = False`（既定）を追加。True の時だけ、アプリ（GameSession の週次抽選）と同じ「固有9＋16＝25種・週頭の状態で判定・確定発火が立つ週は抽選しない・上限15回」で動く。False は従来と同一（golden 差分なし・check_golden_sync OK・swift test 238 件 green）。
- 帯の差（全部入り・ネタ込み・n=1000）：一番大きいのはローテの決勝到達 19.8→33.6%（+13.8pt）。必要充足 +7.0pt・やり込み +6.9pt・のんびり改 −1.6pt。10年目の所持金（中央値）は 578/1337/1366/584万 → 716/1682/1602/690万。
- 決めない：実測の既定を True にするか（§3）。注意：差の大半は「早い時期の知名度の小さな底上げ」が変な仕事の罠（知名度<20）を抜ける速さに効くため。

節構成：§1 何を合わせたか・未対応 ／ §2 帯の比較表 ／ §3 所見

## §1 何を合わせたか・未対応
参照：event_gate_parity_v0.md §1/§2。アプリ＝GameSession.swift（evaluateChoiceEventFire・rollWeeklyRandomEvent・weeklyExtraGate・upcomingStages）＋ChoiceEvent.swift（weeklyBandFireable・choices）。sim＝run_year の「通常行動」直前に `_app_week_event`（`sim_career.py` の EVENTS_APP 節）。

| 項目 | アプリ | EVENTS_APP=True の sim |
|---|---|---|
| プール | 固有9＋16＝25種を一様 | 同じ（APP_POOL）。汎用18種・SEASONAL は使わない |
| 判定する状態 | 週頭（行動前） | 行動前に判定（バイト回数も前週まで） |
| 抽選 | 12%で成立→発火帯・未発火・選べる選択肢ありの候補から一様 | 同じ。乱数は本編 rng と独立（s._app_rng＝アプリの UI 乱数に相当）。本編の乱数列は動かさない |
| 上限 | 週次の通算15回（確定発火は数えない） | APP_EVENT_CAP=15 |
| 年の上限 | 無し（kouhai の2年目以降のみ） | 同じ |
| 次の本番までの週 | upcomingStages（資格あり大会・生存中のGP回戦・決勝/資格ある敗者復活） | `_app_stages` で同じ構成 |
| homecoming | 週38+・4週以上先（>3） | 同じ（>3。旧 sim は>=3） |
| senpai・festival | 本番まで2週以上（本番が無ければ可） | 同じ（本番が無ければ99週先） |
| 固有9種の効果 | choices の値 | 同値。ボット方針は『体力50+なら体力を払う A、なければ B』型（_app_apply） |
| 確定発火の優先順 | justLost > styleTalk > passFork > 前夜 > earlyFormality > tsuuka > nameless > taniguchi > 週次抽選 | 同じ順。条件も同じ（連敗・通過直後・格の高い本番・相性帯・3週内に本番なし） |

ボット方針（決めていない仮置き）：justLost＝体力50+でA／それ未満で金1500+ならC／他はB。styleTalk＝B（相性を削らない）。passFork＝体力50+でA。前夜＝体力60+でA。tsuuka・earlyFormality＝体力50+でA。taniguchi＝体力35+でA（+15万）。

## §3 所見（決めない）
- 差の出方：False（従来）は「汎用18種・発火帯無しの34種一様＋不発」で、旧プールの効果が小さい割に総発火が少なかった。True は固有9種＋確定発火（passFork 知名度+3・taniguchi +15万・justLost 最弱+2 等）が早い時期に入り、15回の上限まで毎回使い切る。off との差から、知名度の上乗せが「知名度<20で本来のオファーが小銭仕事に化ける」罠（EVENTS_ON の変な仕事）を早く抜ける効果が大きいと見える（ローテで特に大きい）。つまり True の数字は「イベントの強さ」より「序盤の知名度の底上げ」の影響が大きい可能性がある。この仮説は未検証（変な仕事をアプリが持つかの確認とセットで）。
- 解散％は True の方が低い（0.4→0.1、0.3→0.0）：tsuuka・earlyFormality・styleTalk などの相性ボーナスが入るため。
- 選択肢（決めない）
  A. 今後の実測は EVENTS_APP=True を既定の前提にする（推奨）。理由：アプリの実プレイに近い分布で決勝到達・所持金を読める。ただし既存の docs の数字（False 基準）とは直接比べられなくなるので、比較する時は両方を併記する。
  B. 既定は False のまま、イベントに触れる実測だけ True で併走する。理由：既存の基準（golden・過去の表）を動かさない。ただし、イベントを含む結論が実機より甘く／辛く出る恐れが残る。
  C. 先に「変な仕事」と riftWarning・weekendInvite の対応状況を確かめてから決める。理由：差の主因の仮説（序盤の知名度の底上げ）が正しいかが分かるまで、True の数字を基準にするのは早い。
  推奨：C を先に（小さな調査）→ A。
