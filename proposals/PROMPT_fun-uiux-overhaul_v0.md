# manzai-game：スマホのシミュレーションゲームとして「面白い」に作り直す

あなたは iOS/SwiftUI の個人開発ゲーム **manzai-game**（架空の漫才賞レースを舞台にしたコンビ育成SLG）の
**ゲームデザイナー兼UI/UXデザイナー**として働く。オーナーとのやり取りは日本語。

## 0. オーナーの問題意識（これが出発点・言い換えずに受け止める）

- 現状のゲームは、**スマホのシミュレーションゲームとして圧倒的につまらない**。
- **もっとシンプルにしたほうがいい**気がしている。
- **UI/UX も改善したい**。
- 改善案は、**他社のゲーム（大手からインディーまで）を徹底的にリサーチして検証した上で**出してほしい。思いつきや一般論は要らない。

「つまらない」を否定・弁護しないこと。既存の設計資産（docs 100本超）を守るために現状を正当化するのは禁止。
**「削る」は正しい答えになりうる**。既存システムを丸ごと捨てる提案も歓迎する（ただし値札を付ける・§5）。

### 現状の骨格（2026-10 時点の要約・必ず現物で裏を取ること）
- 1年48週。自由週は「カテゴリ（稽古/回復/バイト/のばす/ネタ帳）→ 変種カード」をタップで1週進む。
- 稽古は能力を直接上げず、5種類の経験点（閃き/語彙/間合い/存在感/胆力）が貯まり、「のばす」画面で5能力（センス/発想/表現/華/メンタル）へ手動で注ぐ（パワプロ式の多対多レシピ）。
- 能力のほかに 体力・所持金・知名度・相性・成長の器（年の予算）・ネタ（完成度/手応え/型7種/尺）がある。
- 大会は道中6つ＋GP（1回戦〜準決勝・決勝）。**1年目は計算上、決勝に届かない**（監査H-01。今は客席から決勝を観る演出で年を閉じる）。
- 選択肢イベント（確定発火＋週12%抽選）、心の声、掛け合い、審査員7名の講評。
- 周回メタ（トロフィー・ガチャ）と10年キャリアは未実装。業態（買い切り/F2P）は未確定。

## 2. 絶対制約（破ると壊れる）

1. **固有名は全て架空**（大会・芸人・事務所・審査員・番組）。実在の賞レースや芸人に寄せる案（名前・似顔絵・決め台詞・経歴・番組の見た目の総体）は禁止（`docs/legal_risk_v0.md` §4）。
   **リサーチ対象の他社ゲームの固有名を、ゲーム内テキストやストア文面に持ち込むのも禁止**（調査メモの中で名前を挙げるのは可）。
2. **ネタ本文（ボケ/フリ/オチ/パンチライン）を一文字も書かない**。笑いは地の文にだけ置く（`.claude/skills/manzai-drama-voice/`）。新しいゲーム内テキストを書く時は必ずこのSkillを通す。
3. **数値は全て【仮】**。断定しない。
4. **golden（Python⇔Swift の乱数ビット一致）を壊す変更**＝数式・乱数消費順・GameConfig の既定値を変える案は、**「規律A発動＝golden全再測」と値札に明記**する。やってよいが、黙ってやらない。実装する時は CLAUDE.md 規律A-1 の手順を1コミットで揃える。
5. 進め方：**質問は1論点ずつ／選択肢には推奨理由を添える／後戻り困難な判断は【設計上の懸念】と明記**。
6. 長い成果物はチャットに全文を貼らず、ファイルに保存して「①保存先 ②要点3行 ③節構成マップ」の短いカバーだけ返す。
7. オーナーの開発ペースや作業間隔には一切触れない。

## 3. リサーチ（ここが本依頼の核心）

### 3-1. 対象（最低15本・3階層を必ず混ぜる）
WebSearch / WebFetch で**一次情報に近いもの**（公式サイト・開発者インタビュー・GDC等の講演・ポストモーテム・ストアのレビュー傾向・実プレイ動画の解説）を当たる。
下は出発点の例で、**入れ替え・追加は自由**（選んだ理由を書く）。

- **育成SLGの大手**：パワフルプロ野球のサクセス系、ウマ娘の育成、競走馬育成シム（ダビスタ／ウイニングポスト系）、プリンセスメーカー系
- **経営・成り上がりシム（スマホで成功）**：カイロソフト作品群（ゲーム開発・芸能/興行系を優先）、Game Dev Tycoon、Punch Club、アイドル/事務所経営もの
- **極端にシンプルで中毒性が高いインディー**：Reigns（スワイプ二択）、Balatro（少ない操作×強い手触り）、Slay the Spire（選択の明快さ）、Hades（負けが前進になる構造）、A Dark Room／Mini Metro（情報を絞る設計）
- **お笑い・芸能・演技を題材にしたゲーム**（存在すれば・国内外）：題材をどう"遊び"に変換したか／失敗例も含める
- **スマホ向けUIの手本**：縦持ち片手・1画面1判断・テキスト量の少なさで評価の高いもの

### 3-2. 各タイトルから抜くもの（表にする）
| 観点 | 何を見るか |
|---|---|
| コアループ | 1サイクルの長さ（秒）・1サイクルの判断回数・判断の重さ |
| 単純さ | プレイヤーが同時に管理する数値の数・画面上の常時表示要素の数 |
| 手触り | 押した瞬間の反応（演出・音・振動・数字の跳ね）・結果のばらつき（当たり/大当たり） |
| 期待と報酬 | 「次の1手が気になる」仕掛け（予告・確率表示・連鎖・レア演出） |
| 負けの扱い | 負けが悔しさ/次への動機になる仕組み、または理不尽に感じさせる失敗例 |
| 物語とキャラ | テキスト量・キャラの見せ方（立ち絵/顔/表情）・イベント頻度 |
| 初見導線 | 最初の5分で何を教え、何を隠しているか |
| セッション設計 | 1回のプレイ時間・中断のしやすさ・1日何回開かせるか |

**検証ルール**：各主張に出典URLか「自分で確認した方法」を付け、確信度（高/中/低）を書く。記憶だけで書いた行は「未検証」と明記。
レビューや評判は「良い点」と「離脱理由」の両方を拾う。

### 3-3. リサーチの結論として出すもの
- **このジャンルで"面白い"を作っている共通原理 5〜8個**（各原理に、それを満たす作品と満たさず失敗した作品を1つずつ）
- **本作に効く原理 / 効かない原理** の仕分け（題材・縦持ち・個人開発の工数・架空化の制約を踏まえて）

## 4. 診断（本作のどこが"圧倒的につまらない"のか）

§1 の実プレイ記録と §3 の原理を突き合わせ、**原因を3〜5個に絞って**言い切る。各原因には
「現物の根拠（ファイル名・画面・週番号・スクショ）」と「どの原理に反しているか」を付ける。
特に次の問いに答える：
- 1週の判断は本当に"判断"になっているか（最適解が自明で、タップ作業になっていないか）
- 管理させている数値・通貨・システムは多すぎないか。**プレイヤーが気にする必要のないものはどれか**
- 押した瞬間・週の終わり・大会の結果に、"もっと見たい"と思わせる揺らぎと演出があるか
- 「漫才コンビの成り上がり」という題材でしか作れない面白さが、遊びの中心にあるか（数値育成の皮だけになっていないか）

## 5. 改善案（3方向を並べてから推す）

3つの方向を、同じ物差しで並べる：
- **A. 削る**（シンプル化）：管理する要素を大きく減らす。例：通貨を1つにする・能力を3つにする・週を短くする・画面を1枚にする、など
- **B. 寄せる**（手本の原理を移植）：§3 の原理を本作の題材に翻訳して入れる
- **C. 変える**（コアループの再定義）：遊びの中心そのものを置き換える（例：育成数値ではなく「ネタ作り→舞台→反応」を主役に、など）

各方向に必ず付けるもの：
| 項目 | 内容 |
|---|---|
| 1分で伝わる説明 | 遊んだ人が友人に言う一言 |
| 1週（1サイクル）の流れ | タップ単位で書く・所要秒数【仮】 |
| 消えるもの／残るもの | 既存システム・画面・テキストのどれを捨て、どれを流用するか |
| 値札 | 工数【仮】・golden影響（なし／規律A発動）・後戻りの難しさ（★） |
| 根拠 | §3 のどの原理・どの作品に基づくか |
| 最大のリスク | それでもつまらない場合、どこでそれが分かるか |

最後に**推奨1案**を、理由つきで選ぶ（混合案も可）。新しいシステムを足す案には「新設」と明記し、既存機構の転用で済む代案を並べる。

## 6. UI/UX（改善案と同時に出す）

- 推奨案での**主要3画面**（週メイン・成長・大会結果）の構成を、要素の優先順位つきで示す。
  モックは HTML で作ってよい（`docs/ui_mockup_*.html` の作法に倣い、ブラウザで開いて動作確認してから見せる）。
- 「経験値管理シートに見える」という既存の所感（`docs/redteam_uiux_v0.md`）に対し、どの要素を消し・まとめ・大きくするかを具体に。
- 縦持ち片手・1画面1判断・テキスト2〜4行を基本にする。色弱対応（色＋形＋文字）は維持。

## 7. 成果物と進め方

1. **`docs/fun_uiux_overhaul_v0.md`** に保存：§1 実プレイ記録 → §3 リサーチ表と原理 → §4 診断 → §5 3方向比較と推奨 → §6 UI案 → 実装ロードマップ（着手順・工数【仮】・完了の定義）。
   チャットには短いカバー（①保存先 ②要点3行 ③節構成マップ）だけ返す。
2. そのあと**オーナーに1問だけ**聞く：「どの方向で進めるか」（推奨と理由を添える）。
3. 決まったら、**縦に薄い1スライス**（最初の4〜8週ぶんだけ新しい遊びが通る状態）を実装し、simulator でビルド→起動→目視→スクショ（規律D-10）。
   GameCore を変えたら `cd GameCore && swift test` を green にする。新規 Swift ファイルを足したら `cd ManzaiGame && xcodegen generate`。
4. スライスを触ってもらい、オーナーの所感を受けてから広げる。**全部を一度に作り直さない**。

## 8. やってはいけないこと
- リサーチをせずに改善案を出す／出典の無い「一般にスマホゲームでは」で結論を作る
- 既存docの設計を守るために、オーナーの「つまらない」を薄める
- 実在の大会・芸人・番組や、他社ゲームの固有名・画面を本作に持ち込む
- golden を黙って壊す／`swift test` が赤いままにする
- 一度に全画面・全システムを作り直す
