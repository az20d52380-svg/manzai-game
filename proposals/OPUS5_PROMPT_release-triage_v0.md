# 早期リリースのための三大論点 — レッドチーム×ブルーチーム協議依頼

manzai-game は iOS/SwiftUI の「漫才師コンビ育成SLG」MVP（48週×1年、稽古→大会→リザルト→周回）。
**オーナーの目的はただ一つ：このゲームを改善して早くリリースすること。** 設計ドキュメントは既に約1万行あるのに対し、
動いているコードは約1,500行（うちバランス計算が大半）で、コンテンツはほぼ0本しか配線されていない
——つまり「設計しすぎて出荷が遅れる」病気に既にかかっている自己診断がある（`docs/game_reality_check_v0.md`）。

**この協議の成果物は「さらに詳しい設計」ではなく「削る/残す/延期するの意思決定」でなければならない。**
分析のための分析はオーナーが一番嫌う結果。各論点は必ず「KEEP／CUT／DEFER（後回し）」のいずれかで着地させ、
その判断がリリース日をどれだけ早める/遅らせるかを見積もった上で述べること。

---

## ★絶対制約（破ると壊れる）

1. **コードを一切書かない**。`ManzaiGame/`・`GameCore/`・`tools/` のファイルを編集しない。
2. **git操作をしない**（commit / push / branch / merge / add は全面禁止）。読み取り専用の `git fetch` / `cat` / `git show` のみ可。
3. **固有名（大会名・芸人名・事務所名・審査員名・番組名）は全て架空のまま**。実在の賞レース・団体名を一切出さない
   ——似顔絵・決めゼリフ・経歴の"雰囲気"を実在に寄せる案も禁止（`docs/legal_risk_v0.md` §4：氏名を避けるだけでは不十分、
   「同定要素の総体」の架空化が必要というのが法務一次まとめの結論）。
4. **バランス数式・乱数消費順（golden）には触れない**。触れる提案をする場合は「規律A発動＝golden全再測が必要」と明記するに留め、
   実測や数値確定はしない。
5. **数値は全て【仮】と明記**。断定しない。
6. 進め方は本プロジェクトの規律に合わせる：**質問は1論点ずつ／選択肢には推奨理由を添える／後戻り困難な判断は
   【設計上の懸念】と明記する**。

---

## 進め方（ワークフロー）

3論点それぞれについて、**同一セッション内であなた自身がブルーチームとレッドチームを演じ分けて殴り合わせ**、
最後にあなた自身が中立の裁定者として結論を出す。片方に有利な結論をあらかじめ決めておかない。

各論点で以下の順に書くこと：

1. **ブルーチーム最終弁論**（現状維持・投資継続を支持する最強の論拠。都合の悪い事実を隠さない）
2. **レッドチーム最終弁論**（削減・撤退を支持する最強の論拠。都合の悪い事実を隠さない）
3. **裁定**：KEEP／CUT／DEFERのいずれか＋理由＋工数見積り（【仮】）＋リリース日への影響（早まる/遅れる/変わらない）
4. 後戻り困難な要素があれば【設計上の懸念】として明記

---

## 論点A：会話（掛け合いテキスト）を全廃し、無会話シミュレーションに舵を切るべきか

**背景**：現行設計（`docs/dialogue_design_v0.md`）の相方「谷口」との掛け合いは、全てこれまでのClaudeセッションが
執筆したサンプル文。オーナーの所感は「Claudeが考える会話は面白くない。かといって自分で会話を考える時間もない」。
一方で `docs/game_reality_check_v0.md` の診断では「コンテンツは数千項目執筆済みだがコードには1本も配線されていない」
——つまり会話は**現時点では実装コストゼロのまま存在する設計上の在庫**であり、全廃しても実装の手戻りは小さい可能性がある。
また文章品質を底上げするための専用Skill（`.claude/skills/manzai-drama-voice/`、感情→物レシピ＋採点ゲート）が
既に構築済みで未活用。

判断すべきこと：
- 会話を**完全に廃止**して数値ループのみのシミュレーションにするか
- 会話を**大幅に間引いて**要所（決勝敗退など、`docs/game_reality_check_v0.md` が「本作で一番面白そうな部分」と
  評価した決勝演出まわりだけ）に絞るか
- 会話は残すが、**manzai-drama-voice Skillを使って品質を底上げする運用**に切り替えるか

ブルーチームが検討すべき論点例：会話がないと「架空の漫才師コンビ育成」という差別化テーマが単なる数値管理ゲームに
戻ってしまわないか／育成SLGでキャラへの愛着を作る主要な導線が会話であることが多い（パワプロ・ウマ娘との比較で
`docs/game_reality_check_v0.md` が同ジャンルの近縁として挙げている）／Skillを使えば「Claudeが考えるとつまらない」
問題自体を解決できる可能性がある。

レッドチームが検討すべき論点例：未配線コンテンツはサンクコストであり削除の心理的抵抗以外に失うものがない／
個人開発最大のドレインは「文章の執筆・レビュー・配線」（`game_reality_check_v0` §4）であり、会話を切れば
その工数がまるごと消える／オーナー自身が「時間がない」と明言している以上、会話に依存する設計は運用が続かない／
無会話でも成立する育成シムのジャンル自体は存在する（数値ループ主体のタイトルは多い）。

## 論点B：UI/UXのどこまでをリリース前に直すべきか

**背景**：直近のUI/UXレッドチームレビュー（`docs/redteam_uiux_v0.md`、2026-08-08時点・4視点合議）で以下が最重度指摘
として挙がっている：

- キャラが無表情の色シルエットで、表情・ポーズ差分が一切ない
- 週メイン画面の中央（一番目立つ場所）に何も表示されていない
- 体力・やる気ゲージが常時表示されていない
- 単漢字バッジ（関/語/闇/存/胆）が凡例なしで出る＝初見では暗号
- ランクバッジが色が違うだけで格上がりの質感演出がない
- 経験点テーブルが罫線のない数字の羅列（Excelそのもの）
- ボタンが押せそうに見えない
- 稽古カードがTo-Doアプリのリストに見える

現状の実装は「5画面のプレースホルダ」段階（`docs/game_reality_check_v0.md` §4）で、UI/演出の設計済み分の
約85%はまだコードになっていない。

判断すべきこと：**個人開発でリリースを早める制約下**で、上記指摘のうちどれが
「これを直さないと初見で離脱される＝出荷ブロッカー」で、どれが「リリース後のアップデートで直せば十分」か
の仕分け。全部やると工数が膨らみリリースが遠のく前提を必ず踏まえること。

ブルーチームが検討すべき論点例：初見の第一印象（表情差分・中央の主役情報・ゲージ常時表示）は数値では測れない
離脱要因であり、ここをケチると「検証①（タップだけの週送りが単調にならないか）」自体が不合格になる
（`game_reality_check_v0` §3-2で既に懸念表明済み）／単漢字バッジの凡例追加やボタンの立体感などは
実装コストが低い割に効果が大きいと明記されている（`redteam_uiux_v0` §5の提案順）。

レッドチームが検討すべき論点例：キャラの表情差分・ポーズ差分はイラスト外注または大量の差分制作が必要で
個人開発の工数を最も圧迫する項目——ここに時間を使うとリリースが最も遠のく／`game_reality_check_v0` の
最終結論は「本を読むな、実機で10分遊べ」であり、UI磨きも同じ「出荷を先延ばしにする新しい言い訳」になりうる／
最初のリリースは"ちゃちくても遊べる"状態で出し、反応を見てから磨く方が総工数が少ない。

## 論点C：M-1グランプリ（賞レース構造）の理解不足という指摘への対応

**背景**：オーナーの所感は「M-1グランプリをあなた（Claude）が理解していないのでゲームの作りが甘い」。
ただし本プロジェクトには**絶対制約**として固有名の完全架空化ルールがあり（`CLAUDE.md` 絶対ルール4）、
`docs/legal_risk_v0.md` §4の法務一次まとめでは実在賞レース名の商標・パブリシティ権・不正競争防止法上の
リスクが「氏名を避けるだけでは防げない」レベルで具体的に指摘されている。一方で、賞レースの**採点作法や
構造そのもの**（ネタの尺・構成技法・審査員ごとの評価軸のブレ・出順効果など）を実在の一次資料
（例：塙宣之『言い訳 関東芸人はなぜM-1で勝てないのか』）から調査し架空翻案する作業は既に一部着手済み
（`docs/judge_preference_research_v0.md`＝実在賞レースの採点作法をWeb調査で分解し架空7審査員へ翻案、
`docs/neta_system_redesign_v2.md`＝ネタ作り→ライブで磨く→持ちネタ帳→大会で選ぶ、という構造化）。
`docs/game_reality_check_v0.md` §5では「笑いの技術（＝唯一のmoat）」だけは本を買う価値があると明言している。

判断すべきこと：
- 賞レース構造の理解を深めるための**追加調査**（実在の一次資料からの構造分析、架空翻案）を今やるべきか
- やるなら、機構（ネタの得点計算・審査員の評価軸・大会進行）にどこまで反映するか。**それとも今の
  `judge_preference_research_v0.md` / `neta_system_redesign_v2.md` の水準で十分か**
- 「甘さ」の正体が構造理解の不足なのか、単に**コードに1行も配線されていない**ことなのか
  （`game_reality_check_v0` §4：ネタ・審査員システムの実装率）を切り分けること

ブルーチームが検討すべき論点例：笑いの構造理解は他ジャンルの育成SLGと決定的に差別化できる唯一のmoatだと
`game_reality_check_v0` 自身が評価している／塙宣之『言い訳』のような一次資料は安価で、審査員講評・ネタ資産の
説得力に直結する／今のjudge_preference_researchは"研究材料"止まりでスコア計算に相性を乗せる採用可否も
オーナー未決のまま（`docs/START_HERE.md` 記載）。

レッドチームが検討すべき論点例：法務リスク（`legal_risk_v0.md` §4）は「実在に寄せるほど危険」と明言しており、
構造理解を深めれば深めるほど"寄せたくなる誘惑"が強まり架空化が甘くなるリスクがある／既に研究doc2本があるのに
未配線＝これ以上調査してもコードに繋がらなければ意味がない（論点Aと同じ「配線工数が真のボトルネック」問題）／
「甘さ」の実態は理解不足ではなくゲームロジックへの実装ゼロであり、追加調査は問題の取り違え。

## 出力フォーマット

1. 論点A→B→Cの順に、上記4ステップ（ブルー弁論／レッド弁論／裁定／設計上の懸念）を書く
2. 最後に**「早期リリースまでの最短ルート」を1枚のロードマップ**としてまとめる：
   - 今すぐやる（リリース前必須）
   - やらない（CUT・理由つき）
   - 後回し（リリース後アップデート・理由つき）
3. 参照した既存docのパスを末尾に列挙する
4. 分量は簡潔に。冗長な前置き・繰り返しの要約は不要。結論と根拠が伝わればよい
