> v1（2026-10-08）。v0（`PROMPT_visual-genre-overhaul_v0.md`）にブルー/レッドチームとサブエージェント運用を足した上位版。v0 は履歴として残す。

あなたは iOS/SwiftUI の個人開発ゲーム **manzai-game**（漫才コンビ育成SLG・48週×1年・タイトル「四分の夜」）の**リード**。オーナーとのやり取りは日本語。
あなた自身は「指揮・統合・最終判断・simulator 操作・コミット」を担い、調査・設計案・批判はサブエージェント（Agent ツール）に並列で投げる。**オーナーはこの依頼でサブエージェントの使用を明示的に許可している。**

## 0. 最初にやること（リードのみ・10分以内）
1. `cd ~/manzai-game` → `git pull --rebase` → `git status`。ブランチ `claude/manzai-slg-foundation-wprqlu`。このMacから push 可（キーチェーンにトークン保存済み）。
2. 前チャットの未コミット変更を片付ける：`ManzaiGame/Sources/CommandData.swift`（バイトを常設の小カードに・オーナー判断 2026-10-08「常備の方がゲームっぽい」）。ビルド→simulator 目視→1コミット。
3. 読む：`CLAUDE.md`（規律A〜E）／`docs/fun_uiux_overhaul_v0.md` の §0・§3・§6（他社23本の原理）／`docs/START_HERE.md` の索引。
4. **simulator の端末をオーナーに1問だけ確認する**（どの端末がオーナー試遊用か）。前チャットでオーナーと同じ端末を同時に操作して試遊を壊した。以後、リードは**オーナー用でない端末**だけを触る。

## 1. オーナーの声（これが評価基準）
- 「**まだまだシミュレーションゲームの領域にいない。育成ゲームの領域にもいない**」
- 「**一気によくしたい**」「いろんな角度から改善したい」
- イントロ（「コンビ、組まへんか」）・イベントの文章画面・決勝/優勝画面が「**暗い・読みにくい・ワクワクしない・UI/UXがゲームっぽくない**」
  - 共通：暗い紫の背景、細い明朝体の小さな文字、薄い灰色の「タップで進む」、人物がただの灰色の形、華やかさの欠如。
  - 明るくポップでチャンキーな週メインと、それ以外の画面の見た目の言葉がちぐはぐ。
- 既決（覆さない）：A「削る」＝1週1タップ・経験点自動注ぎ・実力/相性の2本バー・行動カード4枚＋バイト常設。**％（通過見込み）は出さない**（冷める）。

## 2. 体制（サブエージェントの役割）
| 班 | 人数の目安 | 役割 | 成果物（`docs/visual_overhaul/` 配下） |
|---|---|---|---|
| **リサーチ班 R** | 4〜5 並列 | ジャンルの「画面の作り」を調べる | `research_<lens>.md` |
| **監査班 A** | 2〜3 並列 | 本作の現状を画面ごとに採点 | `audit_<screen-group>.md` |
| **ブルーチーム B** | 3 並列（思想違い） | 直し方を設計する | `blue_<name>.md` |
| **レッドチーム X** | 4 並列（攻撃面違い） | ブルー案を壊しに行く | `red_<angle>.md` |
| **リード（あなた）** | 1 | 統合・判断・simulator・実装・コミット | `docs/visual_genre_overhaul_v1.md`（正本）・モック |

運用ルール：
- サブエージェントは**ファイルに書いて終わる**（チャットに全文を返させない）。リードは各ファイルの要点だけ読んで統合する。
- 並列にできるものは**同じターンでまとめて起動**し、バックグラウンドで走らせる。
- **simulator を触るのはリードだけ**（端末の取り合い防止）。サブエージェントには、リードが撮ったスクショ（`feedback_shots/overhaul_v1/` に保存）とコードを渡す。
- 調査系は Explore／general-purpose、設計・批判は general-purpose。他社タイトル名は調査・設計ドキュメントの中だけで使い、**ゲーム内テキストには持ち込まない**。

## 3. フェーズ（この順番を守る）

### Phase 1 ― 現物を撮る（リード）
iPhone の確認用端末で、新規ゲームから **イントロ→名付け→週メイン（通常/体力ゲート/オファー週）→週次イベント→大会入口→大会結果（通過/敗退）→決勝演出（勝ち版/観客版）→年末リザルト→ネタ帳→カレンダー→設定** を通して撮り、`feedback_shots/overhaul_v1/NN_<screen>.png` に保存する。
- 決勝・優勝は DEBUG の「🏆優勝」導線や `MZ_SMOKE=4/5`・`MZ_UI=*`（`RootView.swift`）を使って短縮してよい。
- tap と screenshot は別ターン。週送り直後はイベントが遅れて出るので、もう一度撮ってから次をタップ。
- 旧セーブを消すには `xcrun simctl uninstall` → install（plist の直接編集は cfprefsd のキャッシュで効かない）。

### Phase 2 ― リサーチ班 R ＋ 監査班 A（並列で同時起動）
**R（各1体・観点違い）**
1. 育成SLGの王道：パワプロのサクセス／ウマ娘／ダビスタ／プリメ・ときメモ系。週送り・会話画面・イベント・育成結果の見せ方。
2. 経営/シミュレーション：カイロソフト系・ゲーム発展国系・TVスタジオ物語系。小さな成功の積み上げ、数字の気持ちよさ、年表・ランキング。
3. 会話・ノベル演出：ADV/ノベルゲーム、スマホ育成ゲームのストーリー画面。立ち絵・名前札・吹き出し・文字送り・背景・SE。
4. ジュース/手触り：Balatro・Slay the Spire・Peglin 等。押した瞬間の反応、数字が跳ねる、結果の溜めと解放。
5. （任意）お笑い・舞台題材のゲームや映像作品の「舞台の空気」の出し方。

各Rの出力：観点表（明るさと色／書体と文字サイズ／会話画面の部品／結果・勝利演出／テンポ／育てている実感の見せ方）＋「本作にそのまま効く原理 5つ」＋「効かない理由つきの原理」。

**A（各1体・画面群違い）**：Phase 1 のスクショとソースを読み、各画面を「育成SLGとしての水準」で 0〜5 点採点し、言い切りで欠点を書く（コード上の当て先 `File.swift:行` つき）。
- A1：イントロ／名付け／イベント文章画面（`IntroFlow.swift`・`ChoiceEventOverlay.swift`）
- A2：大会入口／大会結果／決勝演出／年末（`TournamentResultView.swift`・`FinalsPresentationView.swift`・`YearResultView.swift`・`S6bView.swift`）
- A3：週メイン／ネタ帳／カレンダー／設定／全体の色・書体トークン（`WeekMainView.swift`・`NotebookView.swift`・`Theme.swift`）

### Phase 3 ― ブルーチーム B（3案を並列で）
同じ材料（R・A の全ファイル）を渡し、**思想の違う3案**を独立に作らせる。
- **B1「サクセス路線」**：明るいポップ・チャンキー・立ち絵＋名前札＋吹き出しで全画面を統一。週メインの見た目の言葉を全画面に広げる。
- **B2「舞台演出路線」**：明るい日常パートと、照明・客席・幕の「本番」パートの緩急。暗さは「本番の緊張」にだけ使い、読みやすさと華やかさを両立する。
- **B3「情報設計路線」**：何を大きく・何を消すか。1画面1判断・文字サイズ階層・送りの合図・アクセシビリティ（Dynamic Type・コントラスト比）。

各案の出力：画面ごとの Before→After（部品・色・書体・サイズ・動き・音）、**新設／転用の区別**、工数【仮】、GameCore 影響（原則ゼロ）、オーナーの声のどれを解くか。モックが要る画面は HTML（`docs/visual_overhaul/mock_<案>.html`）を作ってよい。

### Phase 4 ― レッドチーム X（ブルー3案を並列で攻撃）
- **X1 プレイヤー目線**：「これで育成ゲームの領域に入ったと言えるか」を、代表作と並べて辛口に判定。退屈なまま残る所・ワクワクしない所を名指しする。
- **X2 制約監査**：GameCore・golden・乱数消費順・GameConfig 既定値に触れていないか／固有名が架空か／ネタ本文を書いていないか／他社名・他社の固有表現をゲーム内に持ち込んでいないか／％表示が紛れていないか／新規テキストが `manzai-drama-voice` を通る前提か。
- **X3 可読性・アクセシビリティ**：文字サイズ・コントラスト・色覚多様性・片手操作・タップ領域・アニメで読めない時間。
- **X4 実装リスク**：工数の過小評価、SwiftUI での実現性、既存の演出（Beat1/Beat2・決勝演出・トースト）との衝突、後戻りの難しさ、1目的1コミットに割れるか。

各Xは「致命／重大／軽微」で指摘し、**直し方の提案も添える**。リードはブルーに差し戻して最大2往復で改訂させる（X の「致命」がゼロになるまで）。

### Phase 5 ― 統合とオーナー承認（リード）
- 正本 `docs/visual_genre_overhaul_v1.md` に統合：§0 結論（3行）／§1 オーナーの声／§2 リサーチ要約／§3 現状監査（画面×点数）／§4 採用案（どのブルー案のどこを採ったか、なぜか）／§5 レッドの指摘と対処表／§6 画面別の実装計画（順番・コミット単位・工数【仮】）／§7 やらないこと。
- オーナーには**短いカバー**（保存先／要点3行／節マップ）＋必要ならモックの Artifact を出す。質問は1論点ずつ・推奨つき。
- `docs/START_HERE.md` の索引に1行追加（規律C-7）。
- **承認を取るまで実装しない。**

### Phase 6 ― 一気に実装（承認範囲を最後まで）
- 画面ごとに 1目的=1コミット。順番は「共通トークン（色・書体・会話部品）→イントロ→イベント→大会結果→決勝/優勝→年末→残り」。
- 互いに独立した画面は、worktree を分けたサブエージェント（`isolation: "worktree"`）で並列実装してよい。ただし `project.yml`／`Theme.swift` など共有ファイルに触る作業はリードが直列でやり、統合もリードが行う。新規 Swift ファイルを足したら `cd ManzaiGame && xcodegen generate`。
- 各コミットの前に：`xcodebuild` が通る／**simulator で目視**（規律D-10）／スクショを `feedback_shots/overhaul_v1/after_*.png` に保存／レッドの X2・X3 相当の自己チェック。
- `cd GameCore && swift test` は常に green（GameCore は触らない前提）。区切りごとに push。

### Phase 7 ― オーナー試遊
オーナー用端末に新規ゲームを用意して試遊を頼み、次を聞く：①「育成ゲームの領域に入ったか」②一番ワクワクした画面と、まだ暗い・読みにくい画面 ③1週の秒数と、選択に迷った週の数。所感は doc の末尾に記録し、次の一手を1つだけ提案する。

## 4. 絶対制約
- 固有名は全て架空。**ネタ本文を一文字も書かない**。新しいゲーム内テキストは `.claude/skills/manzai-drama-voice/` を通す（UIラベルは既存語を優先）。
- GameCore の数式・乱数消費順・GameConfig 既定値を変えない。変える必要が出たら**規律A（golden 全再測）と明記して、オーナーに聞く**。
- 体感の問題は演出・色・文字・テンポで解き、数値は最後（規律B-5）。
- ％（通過見込み）表示は出さない。
- 長い成果物はファイル＋短いカバー。オーナーのペースや停滞に触れない。

## 5. 完了の定義
1. `docs/visual_genre_overhaul_v1.md`（リサーチ・監査・ブルー3案・レッド指摘と対処・実装計画）がオーナー承認済み。

4. オーナーの試遊所感を記録済み。
